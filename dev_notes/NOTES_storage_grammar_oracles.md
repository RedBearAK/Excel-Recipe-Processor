# NOTES: definedName '=' incident + the storage-grammar oracle regime
# (2026-08-14)

## The incident

First _xlpm-carrying output triggered repair; fnBlankSafe VANISHED from
the name manager (repair deletes invalid definedNames), orphaning the
Export_View LET cell into #NAME? - the cell formula itself SURVIVED,
which localized the defect to the name. Cause: our stored definedName
began with '='. Excel stores definedName content WITHOUT the leading
'=' - the same grammar lesson as <formula1>, one layer up. The '=' was
in the ORIGINAL translate code too; the path had simply never been
Excel-verified (round trips prefer excel_definition, and Excel-authored
attr_text is '='-less).

Fix at the ONE write funnel (write_named_object strips a leading '='
defensively), plus the two producers now emit canonical '='-less forms
(translate_lambda_to_excel, the hand-authored named-formula path).

## Public prior art (the user asked; it settled the diagnosis)

XlsxWriter (Python/C/Rust) documents EXACTLY our transformer grammar -
_xlpm. parameters, _xlfn. LAMBDA name, define_name for named lambdas,
and the calling cell written as a dynamic-array formula. Their
define_name API takes '=...' BY CONVENTION and their serializer STRIPS
it: generated bytes show <definedName>_xlfn.LAMBDA(_xlpm.temp,...)
with no '='. XlsxWriter output is validated upstream against files
created in real Excel, which makes it a legitimate second oracle.
(Also confirmed: comma-spaces survive storage fine - our stripping is
cosmetic; FlexCel's write-up confirms parameter names cannot contain
dots, matching our identifier rules.)

## The oracle regime (the "more than usual testing" answer)

tests/test_excel_storage_grammar_corpus.py pins generated grammar to
TWO independent Excel-verified references:

- ORACLE A: xlsxwriter's serializer, generated fresh at test time -
  named-lambda definedName content ('='-less asserted explicitly) and
  the lambda cell form, from HUMAN-syntax inputs through our full live
  pipeline. xlsxwriter is a dev dependency; the test FAILS LOUD with a
  pip hint if absent (a silently skipped oracle is how drift returns).
- ORACLE B: the harvested real-Excel workbook, now a PERMANENT fixture
  (tests/fixtures/harvest_2026-08-14_lambda_eta_spill.xlsx). Every
  stored form in it - eta GROUPBY, full-lambda GROUPBY, ANCHORARRAY in
  cell and DV formula1, SORT/UNIQUE prefixing - must be reproduced
  byte-wise (whitespace-normalized outside strings) by the pipeline.

RULE going forward: any NEW storage grammar (next up: optional [y]
lambda parameters, named LET formulas) gets a harvest FIRST, the
harvest joins tests/fixtures/, and the corpus test grows a case. No
generated grammar ships on inference again.
